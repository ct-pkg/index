# AN-IDX-5：min-compiler 字段与 .digestignore

追溯：`IDX-5` ｜ 分析日期：2026-11-18 ｜ 主张：REQ

## 1. 问题陈述

意见书 2.1 / 2.2 提出两件事：索引行增加编译器下限字段，以及用文件清单把"什么算
包内容"的定义权交给包作者。两者都触到同一个边界：**这两套语义的权威实现不在本仓。**

- 索引行由 `ct get` 解析。六字段是消费端已交付的格式；追加第七字段是否会破坏旧
  客户端、旧客户端是否忽略未知字段，本仓无法验证，也不能假设。
- 摘要算法在本仓 `tools/gen-index.sh` 与 `ct` 侧各有一份等价实现。只改其中一份，
  生成的行会在消费端报 `does not match the index`。

因此本仓单方面实现这两项，结果是索引行与消费端不一致，属于破坏性变更。

## 2. 范围

**做什么**

- 仅在分析层面登记：记录约束、归属与重新评估的触发条件。
- 约束条件明确后，本仓可承接的只有"按新契约生成行"这一半工作。

**不做什么**

- 不在本仓新增字段、不改摘要算法、不写"客户端会忽略"这类未经证实的假设。
- 不把该条目排进本仓路线图。

## 3. 验收判据

本条目前不可机械验收（归属未定），因此以"重新评估的触发条件"代替验收判据：

| # | 触发条件 | 重新评估时的判据 |
| --- | --- | --- |
| 1 | `ct` 侧发布带编译器下限筛选能力的版本，并给出索引字段契约 | 用该版本真实 `ct get --index` 回放本仓生成的行，`tools/verify-index.sh` 全绿 |
| 2 | `ct` 侧给出可配置的摘要忽略清单（或明确不做） | 本仓与 `ct` 对同一夹具算出相同摘要；`verify-index.sh` 全绿 |

## 4. 依赖与风险

**依赖**：CT 仓的字段契约与摘要算法定义；两者都不是本仓能单方面决定的。

**风险**

- 若先在本仓加字段，消费端可能忽略（无害但无效）或拒绝（索引整体不可用）；触发
  信号是 `ct get` 报格式错误。
- 若只在本仓改摘要排除清单，所有既有行的摘要与真实树不一致；触发信号是
  `verify-index.sh` 大面积失败。这是不可逆的发布事故，必须两侧同改同发。
